## 子任務拆分

### Task 4.1：估算準確度量測

**產出**
- `tests/test_multimodal.py`（自 `test/test_multimodal.py` 搬移並擴充）
- `tests/rate_limiter/test_estimation_accuracy.py`（新增）

**要求**

1. 以 `git mv` 將 `test/test_multimodal.py` 搬至 `tests/`，保留其可直接執行的 CLI 形式（`--limit`、`--image`、`--prompt`、`--max-side`）。
2. 新增誤差量測模式：每張影像跑完後，比對 trace 記錄的 `reserved` 與 `raw_responses` 的實際 `total_tokens`，全部跑完後輸出統計：
   - 平均高估倍率
   - 最大高估倍率
   - **是否出現任何低估**（這是最重要的一項，低估會導致 429）
3. 量測口徑必須明確：`reserved` 本就包含 `output_buffer × max_tokens` 與各項 pad，比對時應扣除或在輸出中明確標註口徑，否則統計會系統性偏高而失去意義。
4. `tests/rate_limiter/test_estimation_accuracy.py` 為不需外部服務的單元測試：以合成的 message list 與已知尺寸影像，驗證 `estimate_input_tokens` 的分項加總等於 `total`、各分項歸屬正確。

**Codex 複查重點**
- 誤差統計的口徑是否公平（見要求 3）—— 口徑錯誤會讓「估算很準」或「估算很爛」的結論都不可信。
- 搬移是否用 `git mv` 保留歷史。

### Task 4.2：實測驗證

**產出**
- `logs/<日期>_test_multimodal-estimation-validation.md`（實測記錄）

**要求**

> 本任務為**人工執行**。依 [testing-strategy.md](../../docs/testing-strategy.md)，涉及付費 API 的測試由 AI 撰寫、人工執行與驗證。

1. AI 負責：準備實測腳本與檢查清單，明確列出每項要人工確認什麼、預期值範圍是多少。
2. 人工執行項目：
   - **本地 Ollama**：含影像請求，確認 `reserved` 為數千級、三個等待階段的 `wait_s` ≈ 0
   - **雲端 vision 模型**（`gpt-4o` 或 Gemini，擇一）：單張 1024×1024 影像，確認預扣量合理、無 TPM 卡死、無 429、退款正確發生
3. 實測結果記錄於改動日誌，包含實際數值而非只寫「通過」。
4. 若雲端實測發現估算誤差超出可接受範圍（**建議基準：高估不超過實際的 3 倍，且完全不得低估** —— 此基準為初步設定，實測後可與使用者討論調整），停下來報告，不要自行調整公式湊數字。

**Codex 複查重點**
- 檢查清單是否具體到「人工照著做就能執行」，而非泛泛地寫「驗證功能正常」。

### Task 4.3：專案文件更新

**產出**
- `README.md`（修改）
- `docs/TROUBLESHOOTING.md`（修改）

**要求**

1. **重寫〈影像輸入與 TPM 預扣〉整節**：改為說明分項估算機制、各供應商估算器的涵蓋範圍、fallback 行為、如何為新供應商新增估算器（對應 architecture.md 原則 4：只准加不准改）。移除「雲端模型目前尚未支援」的整段限制說明。
2. **〈已知限制與故障排除〉**：移除已修復的兩條（`MODEL_LIMITS` KeyError、雲端 vision 不支援），改列新的實際限制：
   - 遠端 URL 影像無法取得尺寸 → 走保守預設值
   - 未涵蓋的供應商 → fallback 估算，建議自行新增估算器
3. **〈速率限制說明〉**：新增 policy 一覽表與選用建議（雲端 → `enforced`；本地／自架 → `concurrency_only`），說明優先序 YAML > `MODEL_LIMITS` > `DEFAULT_POLICY`。
4. **多模態範例段**：移除「別忘了在 `MODEL_LIMITS` 加入該模型名稱，否則取得 bucket 時會拋出 `KeyError`」的提醒，改為說明建議宣告 `concurrency_only`。
5. `docs/TROUBLESHOOTING.md` 新增條目：預扣估算異常的排查步驟 —— 看 trace 的 `image_tok` / `text_tok` 分項 → 確認估算器是否命中 → 確認尺寸是否解析成功 → 確認模型名前綴比對。

**Codex 複查重點**
- README 的 policy 說明與 `limits_parameters.py` 的實際預設值一致。文件與實作不一致比沒有文件更危險 —— 讀者會照文件寫設定。
- 是否有遺漏的過期敘述（建議全文搜尋 `KeyError`、`尚未支援`、`50000000` 等關鍵字）。

## 驗收流程

1. `uv run pytest` → 全綠。
2. 人工執行 Task 4.2 的實測清單，記錄實際數值。
3. 通讀 `README.md`，逐項對照程式碼確認無過期敘述（重點搜尋 `KeyError`、`尚未支援`、`50000000`）。
4. 確認 `docs/llm-integration.md` 的改動已取得使用者確認。
5. 撰寫改動日誌至 `logs/`，明確標注哪些測試由人工執行、結果為何。
6. 人工決定是否執行 `scripts/merge-to-main.sh dev_ai` 合併回 main。

## 已知風險與注意

- **不要在未取得確認前修改 `docs/llm-integration.md`**（Task 4.4 要求 3）。它被其他專案共用。
- **不要為了讓實測數字好看而調整估算公式**。公式的正確性依據是供應商文件，不是實測誤差。若實測與文件推導不符，那是需要報告的發現，不是需要掩蓋的偏差。
- **不要在文件中寫入未實測的宣稱**。例如若只實測了 `gpt-4o`，就不要在 README 寫「已支援所有 OpenAI vision 模型」。
- **不要修改 `README.md` 中與本輪無關的段落**（安裝、快速開始、API 參考等）。
- 若 Task 4.2 的雲端實測因為沒有 API key 而無法執行，**停下來報告**，不要跳過該任務逕自宣稱完成。
